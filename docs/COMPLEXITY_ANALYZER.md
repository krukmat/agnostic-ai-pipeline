# Complexity Analyzer - Heuristic Story Classification

## Overview

The Complexity Analyzer is a heuristic-based system that automatically classifies user stories as `simple`, `medium`, or `complex` without requiring LLM calls. It analyzes story descriptions and acceptance criteria using keyword matching and scoring rules.

## Purpose

When the Architect LLM doesn't generate the `complexity` field (despite being marked as mandatory in the prompt), the `fix_stories.py` script uses this analyzer to intelligently auto-classify stories instead of defaulting all stories to `medium`.

## How It Works

### Scoring System (0-100 points)

The analyzer evaluates four dimensions:

1. **Keywords (40 points max)**
   - **Simple keywords** (+10): crud, get, post, list, view, display, basic, endpoint, health
   - **Medium keywords** (+25): api, auth, validation, cache, async, webhook, jwt, middleware
   - **Complex keywords** (+40): distributed, microservice, architecture, migration, encryption, scalability, event-sourcing, cqrs

2. **Acceptance Criteria Count (30 points max)**
   - ≤2 criteria: +10 points
   - 3-4 criteria: +20 points
   - ≥5 criteria: +30 points

3. **Description Length (15 points max)**
   - <20 words: +5 points
   - 20-49 words: +10 points
   - ≥50 words: +15 points

4. **Technical Depth Indicators (15 points max)**
   - Keywords like: database (+5), migration (+10), transaction (+5), concurrent (+10), algorithm (+10), performance (+5), etc.
   - Capped at 15 points total

### Classification Thresholds

- **0-34 points**: `simple`
- **35-64 points**: `medium`
- **65-100 points**: `complex`

## Usage

### Automatic (via fix_stories.py)

When you run `fix_stories.py`, it automatically uses the analyzer:

```bash
PYTHONPATH=. .venv/bin/python scripts/fix_stories.py
```

**Output example**:
```
[fix_stories] Missing complexity for story S1, auto-classified as simple
[fix_stories] Missing complexity for story S2, auto-classified as simple
[fix_stories] Missing complexity for story S3, auto-classified as medium
```

### Programmatic

```python
from scripts.utils.complexity_analyzer import analyze_story_complexity

story = {
    "id": "S1",
    "description": "Create GET endpoint for health check",
    "acceptance": ["Returns 200 OK when service is up"]
}

complexity = analyze_story_complexity(story)
print(complexity)  # Output: "simple"
```

### Batch Analysis

```python
from scripts.utils.complexity_analyzer import analyze_stories_batch

stories = [...]  # List of story dicts
results = analyze_stories_batch(stories, verbose=True)

for story_id, complexity in results.items():
    print(f"{story_id}: {complexity}")
```

### Distribution Report

```python
from scripts.utils.complexity_analyzer import get_complexity_distribution

stories = [...]
distribution = get_complexity_distribution(stories)

print(distribution)  # {'simple': 5, 'medium': 3, 'complex': 2}
```

## Benefits

✅ **Intelligent defaults**: Better than hardcoding `medium` for everything
✅ **No LLM required**: Fast, deterministic, free
✅ **Routing optimization**: More stories classified as `simple` → cheaper models used
✅ **Explainable**: Scoring system is transparent and debuggable
✅ **Overrideable**: Users can manually edit complexity if analyzer is wrong

## Limitations

❌ **Less "intelligent" than LLM**: Doesn't understand semantic nuance
❌ **Keyword-dependent**: Unusual descriptions may be misclassified
❌ **Requires maintenance**: Keyword dictionaries need periodic updates
❌ **Boundary cases**: Stories near thresholds (e.g., score=34 vs 35) may vary

## Configuration

### Adjusting Thresholds

Edit `/Users/matiasleandrokruk/Documents/agnostic-ai-pipeline/scripts/utils/complexity_analyzer.py`:

```python
# Current thresholds
if score < 35:
    complexity = 'simple'
elif score < 65:
    complexity = 'medium'
else:
    complexity = 'complex'
```

To make it easier to get `simple` classification:
```python
if score < 40:  # Raised threshold
    complexity = 'simple'
```

### Adding Keywords

Add domain-specific keywords to the dictionaries:

```python
MEDIUM_KEYWORDS = [
    'api', 'integration', 'auth',
    # Add your keywords here:
    'payment', 'invoice', 'shipping'
]
```

## Integration with Complexity Routing

The analyzer output feeds directly into the complexity routing system:

```
Story S1 (no complexity field)
  → fix_stories.py detects missing field
    → analyze_story_complexity(S1) → "simple"
      → Story updated: complexity: simple
        → Developer role uses complexity routing
          → [ROUTING] dev/simple -> ollama/qwen2.5-coder:7b
            → Code generated with cheaper model ✅
```

**Cost savings**: Using simple classification enables cheaper model usage where appropriate, potentially reducing API costs by 50-80% for basic CRUD stories.

## Maintenance

### When to Update Keywords

- New technologies emerge (e.g., new frameworks, patterns)
- Domain-specific terms identified (e.g., industry jargon)
- Misclassifications observed in production

### Monitoring Accuracy

Track manual overrides:
```bash
git log --grep="complexity" planning/stories.yaml
```

If many stories are manually changed from analyzer's classification, consider adjusting thresholds or keywords.
